# 1. Описание проекта

## 1.1 Назначение

Real-Time Team Messenger — веб-приложение для обмена сообщениями между пользователями в режиме реального времени.

Проект представляет собой корпоративный мессенджер, аналогичный Slack или Discord, предназначенный для командного общения, создания рабочих комнат и обмена сообщениями между участниками.

Основная цель проекта — разработка полноценной системы с REST API, WebSocket-соединениями, асинхронной обработкой событий, JWT-аутентификацией и контейнеризацией.

---

# 2. Цели проекта

В рамках проекта необходимо реализовать:

- регистрацию и авторизацию пользователей;
- безопасное хранение учетных данных;
- подтверждение электронной почты;
- управление пользовательским профилем;
- создание рабочих комнат;
- управление участниками комнат;
- обмен сообщениями в реальном времени;
- историю сообщений;
- уведомления пользователей;
- асинхронную обработку событий;
- REST API для взаимодействия с клиентом;
- WebSocket для передачи данных в реальном времени.

# 4. Функциональные требования

---

# 4.1 Пользователи

Система должна поддерживать:

- регистрацию пользователя;
- авторизацию;
- выход из системы;
- обновление токенов доступа;
- подтверждение email;
- просмотр профиля;
- изменение данных профиля;
- изменение пароля;
- изменение аватара.

---

# 4.2 Авторизация

Система должна использовать JWT-аутентификацию.

Требования:

- Access Token используется для доступа к защищенным ресурсам;
- Refresh Token используется для обновления Access Token;
- Refresh Token хранится на сервере только в виде hash;
- пароли пользователей хранятся только в виде криптографического хэша.

---

# 4.3 Комнаты

Пользователь должен иметь возможность:

- создать комнату;
- удалить комнату;
- просмотреть список своих комнат;
- получить информацию о комнате;
- добавить участников;
- удалить участников.

---

# 4.4 Сообщения

Пользователь должен иметь возможность:

- отправить сообщение;
- получить историю сообщений;
- редактировать собственные сообщения;
- удалить собственные сообщения.

Удаление сообщений должно выполняться посредством Soft Delete.

---

# 4.5 Реальное время

Система должна обеспечивать передачу новых сообщений без обновления страницы.

Для этого используется WebSocket.

Пользователь после подключения получает:

- новые сообщения;
- изменения сообщений;
- удаление сообщений;
- системные события комнаты.

---

# 4.6 Email уведомления

Система должна поддерживать отправку email:

- подтверждение регистрации;
- приглашение в комнату;
- сервисные уведомления.

---

# 4.7 Асинхронные события

Система должна использовать Kafka для обработки событий.

Примеры событий:

- создание сообщения;
- отправка email;
- системные уведомления;
- логирование действий.

---

# 5. Нефункциональные требования

Система должна:

- поддерживать асинхронную обработку запросов;
- иметь модульную структуру;
- поддерживать масштабирование;
- использовать миграции базы данных;
- использовать контейнеризацию Docker;
- предоставлять OpenAPI документацию;
- иметь автоматизированное тестирование.

---

# 6. Безопасность

Система должна обеспечивать:

- безопасное хранение паролей;
- JWT-аутентификацию;
- проверку прав доступа;
- защиту приватных маршрутов;
- валидацию входных данных;
- защиту пользовательских данных.

---

# 7. Требования к базе данных

База данных должна хранить:

- пользователей;
- комнаты;
- участников комнат;
- сообщения;
- refresh-токены.

Изменение структуры базы данных должно выполняться только через Alembic миграции.

---

# 8. Требования к API

API должен:

- использовать REST архитектуру;
- использовать JSON формат;
- иметь версионирование;
- иметь единый формат ошибок;
- предоставлять OpenAPI документацию.

---

# 9. Ограничения проекта

В рамках первой версии:

- нет видеозвонков;
- нет голосовых сообщений;
- нет мобильного приложения;
- нет сложной системы ролей;
- нет распределенной микросервисной архитектуры.
