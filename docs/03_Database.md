# 1. Общая информация

В качестве основной базы данных используется **PostgreSQL**.

Доступ к базе данных осуществляется посредством **SQLAlchemy 2.x** в асинхронном режиме.

Все изменения структуры базы данных выполняются исключительно через **Alembic**.

База данных используется для хранения пользователей, комнат, участников комнат, зашифрованных сообщений, токенов подтверждения электронной почты и информации об отозванных Refresh Token.

---

# 2. Основные принципы

При проектировании базы данных используются следующие правила:

* основные сущности используют `UUID` в качестве первичного ключа;
* даты и время хранятся в формате `TIMESTAMP WITH TIME ZONE`;
* связи между сущностями реализуются посредством `FOREIGN KEY`;
* удаление сообщений выполняется посредством **Soft Delete**;
* содержимое сообщений хранится в базе данных в **зашифрованном виде**;
* исходный текст сообщения не хранится в открытом виде;
* Refresh Token не хранится в базе данных;
* для отзыва Refresh Token в базе сохраняется только его `jti`;
* verification token хранится только в виде SHA-256 хэша;
* изменение структуры базы данных осуществляется только через миграции Alembic.

# 4. Таблица User

## Назначение

Хранение информации о зарегистрированных пользователях.

| Поле            | Тип                      | Ограничения             | Описание                   |
| --------------- | ------------------------ | ----------------------- | -------------------------- |
| `id`            | UUID                     | PK                      | Идентификатор пользователя |
| `username`      | VARCHAR(50)              | UNIQUE, NOT NULL        | Имя пользователя           |
| `email`         | VARCHAR(255)             | UNIQUE, NOT NULL        | Email пользователя         |
| `password_hash` | VARCHAR                  | NOT NULL                | Хэш пароля                 |
| `avatar_url`    | VARCHAR                  | NULL                    | Ссылка на аватар           |
| `is_verified`   | BOOLEAN                  | DEFAULT FALSE, NOT NULL | Статус подтверждения email |
| `created_at`    | TIMESTAMP WITH TIME ZONE | NOT NULL                | Дата регистрации           |
| `updated_at`    | TIMESTAMP WITH TIME ZONE | NOT NULL                | Дата последнего изменения  |

Пароль пользователя никогда не хранится в открытом виде.

В базе данных сохраняется только безопасный хэш пароля.

# 5. Таблица Room

## Назначение

Хранение информации о чат-комнатах.

| Поле         | Тип                      | Ограничения             | Описание                  |
| ------------ | ------------------------ | ----------------------- | ------------------------- |
| `id`         | UUID                     | PK                      | Идентификатор комнаты     |
| `name`       | VARCHAR(100)             | NOT NULL                | Название комнаты          |
| `owner_id`   | UUID                     | FK(`User.id`), NOT NULL | Создатель комнаты         |
| `created_at` | TIMESTAMP WITH TIME ZONE | NOT NULL                | Дата создания             |
| `updated_at` | TIMESTAMP WITH TIME ZONE | NOT NULL                | Дата последнего изменения |

Каждая комната имеет одного владельца.

# 6. Таблица RoomMember

## Назначение

Связующая таблица между пользователями и комнатами.

Один пользователь может состоять во многих комнатах.

Одна комната может содержать множество пользователей.

Тип связи:

**Many-to-Many**

| Поле        | Тип                      | Ограничения                 | Описание                   |
| ----------- | ------------------------ | --------------------------- | -------------------------- |
| `room_id`   | UUID                     | PK, FK(`Room.id`), NOT NULL | Идентификатор комнаты      |
| `user_id`   | UUID                     | PK, FK(`User.id`), NOT NULL | Идентификатор пользователя |
| `joined_at` | TIMESTAMP WITH TIME ZONE | NOT NULL                    | Дата вступления в комнату  |

Первичный ключ является составным:

```text
(room_id, user_id)
```

Составной Primary Key предотвращает повторное добавление одного пользователя в одну комнату.

# 7. Таблица Message

## Назначение

Хранение сообщений пользователей.

Исходный текст сообщения **не хранится в открытом виде**.

Перед сохранением в PostgreSQL текст сообщения шифруется на уровне приложения.

| Поле             | Тип                      | Ограничения             | Описание                      |
| ---------------- | ------------------------ | ----------------------- | ----------------------------- |
| `id`             | UUID                     | PK                      | Идентификатор сообщения       |
| `room_id`        | UUID                     | FK(`Room.id`), NOT NULL | Комната                       |
| `author_id`      | UUID                     | FK(`User.id`), NOT NULL | Автор сообщения               |
| `encrypted_text` | TEXT                     | NOT NULL                | Зашифрованный текст сообщения |
| `updated_at`     | TIMESTAMP WITH TIME ZONE | NOT NULL                | Дата последнего изменения     |
| `deleted_at`     | TIMESTAMP WITH TIME ZONE | NULL                    | Дата логического удаления     |
| `created_at`     | TIMESTAMP WITH TIME ZONE | NOT NULL                | Дата создания                 |

---

## 7.1. Принцип шифрования

Перед сохранением сообщения приложение выполняет шифрование:

```text
Исходный текст
      ↓
  Encryption
      ↓
encrypted_text
      ↓
 PostgreSQL
```

При получении сообщения выполняется обратная операция:

```text
PostgreSQL
      ↓
encrypted_text
      ↓
  Decryption
      ↓
Исходный текст
```

Таким образом, PostgreSQL не содержит исходный текст сообщения в открытом виде.

---

## 7.2. Ключ шифрования

Ключ шифрования не должен храниться непосредственно в базе данных.

Он должен находиться во внешнем защищённом хранилище конфигурации, например:

```text
Environment Variables
Secret Manager
Docker Secrets
```

База данных хранит только зашифрованное содержимое.

Ключ шифрования не должен:

* храниться в таблице `Message`;
* попадать в Git;
* находиться в исходном коде;
* передаваться клиенту.

---

## 7.3. Требования к алгоритму

Для шифрования сообщений должен использоваться современный алгоритм **аутентифицированного шифрования (AEAD)**.

Рекомендуемый вариант:

```text
AES-256-GCM
```

или другой современный AEAD-алгоритм.

Аутентифицированное шифрование позволяет не только скрывать содержимое сообщения, но и обнаруживать его изменение.

Для каждого сообщения должен использоваться уникальный nonce/IV в соответствии с требованиями выбранного алгоритма.

---

# 7.4. Soft Delete

Сообщения не удаляются физически.

При удалении устанавливается:

```text
deleted_at = current timestamp
```

Если:

```text
deleted_at IS NULL
```

сообщение считается активным.

Если:

```text
deleted_at IS NOT NULL
```

сообщение считается удалённым.

Зашифрованное содержимое удалённого сообщения может сохраняться в базе данных в соответствии с политикой хранения истории.

# 8. Таблица EmailVerification

## Назначение

Хранение информации о токенах подтверждения электронной почты.

Сам verification token в базе данных не хранится.

В базе сохраняется только его SHA-256 хэш.

| Поле         | Тип                      | Ограничения             | Описание                       |
| ------------ | ------------------------ | ----------------------- | ------------------------------ |
| `id`         | UUID                     | PK                      | Идентификатор записи           |
| `user_id`    | UUID                     | FK(`User.id`), NOT NULL | Пользователь                   |
| `token_hash` | VARCHAR(64)              | UNIQUE, NOT NULL        | SHA-256 хэш verification token |
| `expires_at` | TIMESTAMP WITH TIME ZONE | NOT NULL                | Срок действия                  |
| `used_at`    | TIMESTAMP WITH TIME ZONE | NULL                    | Время использования            |
           |

Verification Token считается действительным, если одновременно выполняются условия:

* запись существует;
* `expires_at` больше текущего времени;
* `used_at IS NULL`.

После успешного подтверждения email:

```text
User.is_verified = TRUE
```

и:

```text
EmailVerification.used_at = current timestamp
```

После этого токен считается использованным и не может применяться повторно.

# 9. Таблица BannedRefreshToken

## Назначение

Хранение информации об отозванных Refresh Token.

Сам Refresh Token в базе данных **не хранится**.

Refresh Token представляет собой JWT, содержащий уникальный идентификатор `jti`.

При отзыве токена в базу добавляется его `jti`.

| Поле        | Тип                      | Ограничения          | Описание                     |
| ----------- | ------------------------ | -------------------- | ---------------------------- |
| `jti`       | VARCHAR                  | PK, UNIQUE, NOT NULL | Уникальный идентификатор JWT |
| `banned_at` | TIMESTAMP WITH TIME ZONE | NOT NULL             | Дата и время отзыва токена   |

---

# 9.1. Механизм отзыва Refresh Token

При создании Refresh Token генерируется JWT с уникальным `jti`.

Пример payload:

```text
{
    "sub": "user_id",
    "jti": "unique-token-id",
    "exp": "expiration-time"
}
```

При logout или отзыве токена:

```text
Refresh Token
      ↓
извлечение jti
      ↓
BannedRefreshToken
      ↓
jti сохраняется в БД
```

При попытке использовать Refresh Token приложение:

1. проверяет подпись JWT;
2. проверяет срок действия `exp`;
3. извлекает `jti`;
4. проверяет наличие `jti` в `BannedRefreshToken`;
5. если `jti` найден — токен отклоняется;
6. если `jti` отсутствует — выполняются остальные проверки токена.

# 10. Связи между сущностями

## User → Room

Один пользователь может владеть несколькими комнатами.

Каждая комната имеет одного владельца.

Тип связи:

**One-to-Many**

```text
User 1 → N Room
```

---

## User ↔ Room

Пользователь может состоять во многих комнатах.

Комната может содержать многих пользователей.

Тип связи:

**Many-to-Many**

Связующая таблица:

```text
RoomMember
```

---

## User → Message

Один пользователь может создать множество сообщений.

Каждое сообщение имеет одного автора.

Тип связи:

**One-to-Many**

```text
User 1 → N Message
```

---

## Room → Message

Одна комната может содержать множество сообщений.

Каждое сообщение относится к одной комнате.

Тип связи:

**One-to-Many**

```text
Room 1 → N Message
```

---

## User → EmailVerification

Один пользователь может иметь несколько записей подтверждения email.

Каждая запись подтверждения принадлежит одному пользователю.

Тип связи:

**One-to-Many**

```text
User 1 → N EmailVerification
```

---

## Refresh Token → BannedRefreshToken

`BannedRefreshToken` содержит информацию только об отозванных Refresh Token.

Связь с конкретным Refresh Token определяется через его `jti`.

```text
Refresh Token 1 → 0..1 BannedRefreshToken
```

При этом физического `FOREIGN KEY` между таблицами нет, поскольку сам Refresh Token в БД не хранится.

# 11. Индексы

Для повышения производительности используются следующие индексы.

## User

* `email` — UNIQUE INDEX;
* `username` — UNIQUE INDEX.

## Room

* `owner_id`.

## RoomMember

* составной Primary Key `(room_id, user_id)`;
* `room_id`;
* `user_id`.

## Message

* `room_id`;
* `author_id`;
* `created_at`.

## EmailVerification

* `token_hash` — UNIQUE INDEX;
* `user_id`;
* `expires_at`.

## BannedRefreshToken

* `jti` — PRIMARY KEY / UNIQUE INDEX;
* `banned_at`.

Основной запрос к `BannedRefreshToken` выполняется по `jti`, поэтому Primary Key обеспечивает необходимый индекс.

# 12. Ограничения

## User

* Email должен быть уникальным.
* Username должен быть уникальным.
* Password Hash не может быть `NULL`.

## Room

* Комната должна иметь владельца.
* Владелец должен существовать в таблице `User`.

## RoomMember

Не допускается повторное добавление одного пользователя в одну комнату.

Используется составной Primary Key:

```text
(room_id, user_id)
```

## Message

* Сообщение должно принадлежать существующей комнате.
* Сообщение должно иметь автора.
* `encrypted_text` не может быть `NULL`.
* Исходный текст сообщения не должен сохраняться в открытом виде.
* Для шифрования должен использоваться защищённый ключ.
* При удалении используется Soft Delete.

## EmailVerification

* `token_hash` должен быть уникальным.
* Использованный токен нельзя использовать повторно.
* Истёкший токен нельзя использовать для подтверждения email.

## BannedRefreshToken

* `jti` должен быть уникальным.
* `jti` не может быть `NULL`.
* `banned_at` не может быть `NULL`.
* Повторная запись одного `jti` не допускается.

# 13. Правила удаления данных

## User

Удаление пользователя не должно приводить к физическому удалению его сообщений.

Сообщения должны сохраняться в истории.

Связанные записи:

* `RoomMember`;
* `EmailVerification`;

могут удаляться каскадно.

---

## Room

Удаление комнаты приводит к удалению:

* участников комнаты;
* сообщений комнаты.

Для соответствующих Foreign Key используется:

```text
ON DELETE CASCADE
```

---

## Message

Используется **Soft Delete**.

Запись физически не удаляется.

Устанавливается:

```text
deleted_at = current timestamp
```

---

## EmailVerification

После успешного подтверждения email запись не удаляется автоматически.

Используется:

```text
used_at
```

для фиксации факта использования токена.

Истёкшие или использованные записи могут очищаться отдельной фоновой задачей.

---

## BannedRefreshToken

При отзыве Refresh Token его `jti` добавляется в таблицу `BannedRefreshToken`.

После окончательного истечения срока действия Refresh Token запись может быть удалена фоновой задачей.

Это позволяет избежать постоянного накопления отозванных токенов.

---

# 14. Безопасность хранения данных

В базе данных не должны храниться в открытом виде:

* пароль пользователя;
* Refresh Token;
* verification token;
* текст сообщения.

Используется следующая схема:

| Данные                   | Что хранится в БД        |
| ------------------------ | ------------------------ |
| Password                 | Password Hash            |
| Refresh Token            | `jti` отозванного токена |
| Email Verification Token | SHA-256 Hash             |
| Message Text             | Encrypted Text           |

# 15. Шифрование сообщений

Процесс создания сообщения:

```text
┌──────────────────┐
│   Client         │
│  "Hello World"   │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│     FastAPI      │
│                  │
│    Encryption    │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│    PostgreSQL    │
│                  │
│ encrypted_text   │
└──────────────────┘
```

Процесс получения сообщения:

```text
┌──────────────────┐
│    PostgreSQL    │
│                  │
│ encrypted_text   │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│     FastAPI      │
│                  │
│    Decryption    │
└────────┬─────────┘
         │
         ▼

│     Client       │

└──────────────────┘
```

Ключ шифрования используется только серверным приложением.

# 17. Архитектура хранения токенов

Refresh Token реализуется как JWT.

Сам токен не сохраняется в PostgreSQL.

```text
┌──────────────────────┐
│    Refresh Token     │
│        JWT           │
└──────────┬───────────┘
           │
           │ contains
           ▼
       ┌───────┐
       │  jti  │
       └───┬───┘
           │
           │ logout / revoke
           ▼
┌──────────────────────────┐
│ BannedRefreshToken       │
├──────────────────────────┤
│ jti                      │
│ banned_at                │
└──────────────────────────┘
```

Проверка Refresh Token:

```text
Client
  │
  │ Refresh Token
  ▼
FastAPI
  │
  ├──► JWT signature validation
  │
  ├──► expiration check
  │
  ├──► extract jti
  │
  └──► BannedRefreshToken lookup
              │
        ┌─────┴─────┐
        │            │
      found       not found
        │            │
        ▼            ▼
      REJECT       ACCEPT
```

# 18. Принцип защиты данных

Текущая архитектура разделяет различные способы защиты данных:

### Пароли

Используется одностороннее хэширование:

```text
Password → Password Hash
```

Пароль невозможно восстановить из хэша.

### Verification Token

Используется SHA-256:

```text
Verification Token → SHA-256 → token_hash
```

### Сообщения

Используется обратимое шифрование:

```text
Message → Encryption → encrypted_text
```

Исходное сообщение может быть восстановлено приложением при наличии правильного ключа шифрования.

### Refresh Token

Сам JWT не хранится.

Для отзыва используется:

```text
Refresh Token → jti → BannedRefreshToken
```
